O que esse projeto ensina (e que vale ouro)
1. Arquitetura de 3 camadas bem separadas

Coleta (ESP32 → Zabbix via polling + push híbrido; agentes nos servidores)

Orquestração/estado (Zabbix: itens, gatilhos, macros, templates)

Visualização (Grafana com painel custom em JS/Three.js)

Cada camada pode ser substituída sem quebrar as outras. Isso é o que torna adaptável.

2. Padrões que você deve copiar independente do seu projeto

.env + configurar.py idempotente — nada configurado à mão no Zabbix/Grafana. Isso é ouro.

Template reutilizável + macros — trocar limite de temperatura sem mexer em item.

Item mestre + dependentes — uma requisição HTTP a cada 15s, não onze.

Tags efeito nos gatilhos — o front-end reage pelo efeito, não pelo texto do alerta. Desacoplamento perfeito.

Serviço de ações separado (acoes.py) — porque o plugin do Zabbix bloqueia escrita. Lição valiosa: a ponte só lê, quem escreve é outro serviço com menor privilégio.

Receitas por servidor (/opt/acoes/*.sh + acoes.conf) — o botão é o mesmo, a receita é local. Portável para cloud.

Cache TTL do datasource menor que o ciclo de pergunta — detalhe que quase ninguém acerta.

3. Lições "de guerra" documentadas (essa parte é rara e preciosa)

OTA com dois bancos de flash, por que o .bin mesclado apaga Wi-Fi e o OTA não

Histerese no sensor de chuva (analogia da geladeira)

ADC1 só com Wi-Fi no ESP32

millis() zera a cada 49,7 dias

Port forwarding do Docker quebra após reinício → --force-recreate --no-deps

Plugin Grafana precisa GF_PLUGINS_PREINSTALL_SYNC senão trava na primeira subida

Antes de eu montar o caminho, preciso decidir 4 coisas com você
1. Onde vai rodar o broker MQTT?
Hoje você usa broker.emqx.io (público). Para o laboratório do original (on-premise), o ideal é um Mosquitto local no Docker, porque:

O Zabbix precisa alcançar o broker, e o broker público pode ser lento/bloqueado

Você não quer seus dados de rack circulando num broker público

Fica tudo reproduzível: docker compose up sobe tudo

Pergunta: você tem problema em trocar broker.emqx.io por um Mosquitto local? (É 1 linha no firmware + 1 serviço no compose.)

2. Como o Zabbix vai consumir?
Duas opções:

Opção	Como	Prós	Contras
A) MQTT agent no Zabbix	Item mestre MQTT (esp32.status), JSONPath nos dependentes — igual ao original	Reaproveita o template inteiro, efeito das tags, tudo	Precisa de Mosquitto acessível pelo container do Zabbix
B) Push via Zabbix sender	ESP32 manda Zabbix sender na porta 10051	Funciona como o "push" original, mais rápido	Precisa recompilar o firmware com zabbix_sender, perde HMAC do jeito que está
Recomendação: A. Seu firmware já publica JSON estruturado em status e ambiente. É plug-and-play. E o "push" urgente (pânico, invasão) já vem pelo MQTT em < 1s — a latência que importa.

3. Você quer manter a autenticação HMAC como está, ou o Zabbix também vai mandar comandos?
O original usa dois caminhos separados:

Leitura (polling HTTP) — Zabbix busca

Ação (serviço Python separado, com usuário restrito no Zabbix, que assina HMAC)

Você já tem HMAC + nonce. Isso é ouro para a camada de ações do original: o serviço acoes.py pode assinar comandos com a chave HMAC do firmware (que fica no .env, espelhando a NVS). Aí o botão "DESARMAR" no Grafana → serviço Python → publica MQTT com HMAC → ESP32 executa.

Pergunta: você quer que eu já inclua essa ponte HMAC no plano, ou deixamos ações para a fatia final?

4. Wokwi vs. hardware real
O comentário diz "compatível com Wokwi". Isso muda tudo na prioridade:

Se você está no Wokwi: esqueça OTA, esqueça Docker de gravador, esqueça firewall. O caminho é Wokwi → broker público → Zabbix em Docker no seu PC → Grafana. Muito mais simples.

Se você tem hardware: vale o caminho completo do original (gravador web, OTA, calibração, reserva de IP).

Antes de te entregar os arquivos, preciso te avisar de uma limitação importante do Wokwi que muda o plano:

O Wokwi não alcança o localhost do seu PC. A rede Wokwi-GUEST só fala com a internet pública. Isso significa que o ESP32 simulado não vai conseguir publicar no Mosquitto que roda no seu Docker local (porta 1883).

Isso nos deixa com duas opções realistas para a fase Wokwi:

Opção	Como funciona	Prós	Contras
A) Broker público durante o Wokwi	Firmware aponta para broker.emqx.io (como já está). Seu PC roda um cliente MQTT que assina esses tópicos e repassa ao Mosquitto local, ou o Zabbix lê direto do broker público.	Funciona já	Expõe dados do rack num broker público; latência e bloqueios eventuais
B) Bridge MQTT no seu PC	Um container Mosquitto faz bridge: assina no broker público e republica no local. O Zabbix lê só o local.	Mantém o Zabbix isolado; dados saem do público só no PC	Um passo a mais de configuração
Minha recomendação para o Wokwi: Opção B. Você mantém o firmware exatamente como está (broker público), e o Mosquitto local vira uma "ponte" que puxa os tópicos do broker público para dentro da sua rede Docker. Quando você migrar para hardware real, só troca o endereço do broker no firmware e remove a bridge.

yaml
# docker-compose.yml — base para o Rack Monitor
# Serviços mínimos: broker MQTT + Zabbix + Grafana + Postgres

services:
  # ---------- Broker MQTT local ----------
  mosquitto:
    image: eclipse-mosquitto:2.0
    container_name: rack-mosquitto
    restart: unless-stopped
    ports:
      - "1883:1883"          # MQTT
      - "9001:9001"          # WebSocket (opcional, útil para debug no navegador)
    volumes:
      - ./mosquitto/config:/mosquitto/config:ro
      - mosquitto_data:/mosquitto/data
      - mosquitto_log:/mosquitto/log
    networks:
      - rack-net
    healthcheck:
      test: ["CMD-SHELL", "mosquitto_sub -h localhost -t '$$SYS/#' -C 1 -W 2 || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3

  # ---------- Banco do Zabbix ----------
  postgres:
    image: postgres:16-alpine
    container_name: rack-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - rack-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 10s
      timeout: 5s
      retries: 5

  # ---------- Zabbix Server ----------
  zabbix-server:
    image: zabbix/zabbix-server-pgsql:alpine-7.0-latest
    container_name: rack-zabbix-server
    restart: unless-stopped
    environment:
      DB_SERVER_HOST: postgres
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "10051:10051"        # Zabbix trapper/sender
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - rack-net

  # ---------- Zabbix Web (interface + API) ----------
  zabbix-web:
    image: zabbix/zabbix-web-nginx-pgsql:alpine-7.0-latest
    container_name: rack-zabbix-web
    restart: unless-stopped
    environment:
      ZBX_SERVER_HOST: zabbix-server
      DB_SERVER_HOST: postgres
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      PHP_TZ: America/Sao_Paulo
    ports:
      - "8080:8080"
    depends_on:
      - zabbix-server
      - postgres
    networks:
      - rack-net

  # ---------- Grafana ----------
  grafana:
    image: grafana/grafana:13.2.5
    container_name: rack-grafana
    restart: unless-stopped
    environment:
      GF_SECURITY_ADMIN_USER: ${GRAFANA_ADMIN_USER}
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD}
      GF_INSTALL_PLUGINS: ""   # plugins entram na fatia 3
    ports:
      - "3000:3000"
    volumes:
      - grafana_data:/var/lib/grafana
    networks:
      - rack-net

networks:
  rack-net:
    driver: bridge

volumes:
  mosquitto_data:
  mosquitto_log:
  postgres_data:
  grafana_data:
