🛠️ Passo 2 — Criar o scripts/setup.sh
Este script faz o setup inicial (primeira vez):

bash
cat > ~/Desktop/monitoramento-cpd/scripts/setup.sh << 'SHEOF'
#!/usr/bin/env bash
# ============================================================
# setup.sh — Prepara o projeto para rodar pela primeira vez
# ------------------------------------------------------------
# O que faz:
#   1. Verifica pré-requisitos (Docker, Python 3)
#   2. Cria o .env a partir do .env.example (se não existir)
#   3. Sobe a stack Docker
#   4. Aguarda os serviços ficarem saudáveis
#   5. Cria o venv Python e instala dependências
#   6. Roda o script de IaC do Zabbix
# ============================================================
set -euo pipefail

BASE="$(cd "$(dirname "$0")/.." && pwd)"
cd "$BASE"

echo "============================================================"
echo "  SETUP — monitoramento-cpd"
echo "============================================================"

# 1. Pré-requisitos
echo "[1/6] Verificando pré-requisitos..."
command -v docker >/dev/null 2>&1 || { echo "❌ Docker não encontrado. Instale o Docker Desktop."; exit 1; }
command -v docker compose >/dev/null 2>&1 || { echo "❌ Docker Compose v2 não encontrado."; exit 1; }
command -v python3 >/dev/null 2>&1 || { echo "❌ Python 3 não encontrado."; exit 1; }
echo "  ✅ Docker, Docker Compose e Python 3 encontrados."

# 2. .env
echo "[2/6] Verificando .env..."
if [ ! -f .env ]; then
  cp .env.example .env
  echo "  ⚠️  .env criado a partir do .env.example."
  echo "  ⚠️  EDITE O .env ANTES DE CONTINUAR (senhas do Postgres e do Grafana)."
  echo "  ⚠️  Depois, rode 'make setup' novamente."
  exit 0
else
  echo "  ✅ .env já existe."
fi

# 3. Subir a stack
echo "[3/6] Subindo a stack Docker..."
docker compose up -d
echo "  ✅ Stack iniciada."

# 4. Aguardar saúde
echo "[4/6] Aguardando serviços ficarem saudáveis..."
for i in $(seq 1 30); do
  healthy=$(docker compose ps --format '{{.Health}}' 2>/dev/null | grep -c 'healthy' || true)
  running=$(docker compose ps --format '{{.State}}' 2>/dev/null | grep -c 'running' || true)
  if [ "$healthy" -ge 2 ] && [ "$running" -ge 5 ]; then
    echo "  ✅ $running serviços rodando ($healthy saudáveis)."
    break
  fi
  echo "  ... aguardando ($i/30) — $running rodando, $healthy saudáveis"
  sleep 3
done

# 5. Venv Python
echo "[5/6] Configurando ambiente Python..."
if [ ! -d .venv ]; then
  python3 -m venv .venv
  echo "  ✅ .venv criado."
fi
# shellcheck disable=SC1091
source .venv/bin/activate
pip install --quiet --upgrade pip
pip install --quiet requests python-dotenv
echo "  ✅ Dependências instaladas."

# 6. IaC do Zabbix
echo "[6/6] Configurando o Zabbix via IaC..."
python configurar_zabbix.py

echo ""
echo "============================================================"
echo "  ✅ SETUP CONCLUÍDO!"
echo "============================================================"
echo ""
echo "  Próximos passos:"
echo "    make up        # (re)sobe a stack"
echo "    make ps        # vê o estado dos containers"
echo "    make health    # verifica saúde de todos os serviços"
echo "    make reset     # apaga volumes e recomeça do zero"
echo ""
echo "  Interfaces:"
echo "    Zabbix:  http://localhost:8080 (Admin/zabbix)"
echo "    Grafana: http://localhost:3000 (admin/senha do .env)"
echo ""
SHEOF

chmod +x ~/Desktop/monitoramento-cpd/scripts/setup.sh

#!/usr/bin/env bash

#!/usr/bin/env bash
# ============================================================
# backup.sh — Backup do Postgres (Zabbix) e do Grafana
# ============================================================
set -euo pipefail

BASE="$(cd "$(dirname "$0")/.." && pwd)"
cd "$BASE"

DATA="$(date +%Y%m%d_%H%M%S)"
mkdir -p backups

echo "[1/2] Backup do Postgres (Zabbix)..."
docker compose exec -T postgres pg_dump -U zabbix -d zabbix > "backups/zabbix_${DATA}.sql"
echo "  ✅ backups/zabbix_${DATA}.sql"

echo "[2/2] Backup do Grafana (banco SQLite)..."
docker compose exec -T grafana tar -czf - /var/lib/grafana/grafana.db > "backups/grafana_${DATA}.tar.gz"
echo "  ✅ backups/grafana_${DATA}.tar.gz"

echo ""
echo "✅ Backups salvos em backups/"
SHEOF

*.zip

# ADR-001: Usar Mosquitto local em vez de broker público

- **Status:** Aceito
- **Data:** 2026-11-12
- **Autores:** Cristiano
- **Contexto do projeto:** Fatia 0 (Base Docker)

## Contexto

O firmware do ESP32 (no Wokwi) publica dados via MQTT. Para o Zabbix conseguir
ler esses dados, precisa haver um broker MQTT acessível.

As opções eram:

1. **Broker público** (`broker.emqx.io`): o que o firmware já usava.
2. **Broker local** (Mosquitto em Docker): na rede `cpd-net`.
3. **Híbrido** (ponte entre os dois).

O projeto precisa ser **reproduzível** e **isolado** (não expor dados do CPD
a terceiros).

## Decisão

Usar um **Mosquitto local** em Docker (`cpd-mosquitto`), na rede `cpd-net`.
O firmware continua publicando no broker público (por causa do Wokwi), mas
o Mosquitto local **puxa** esses dados via **bridge MQTT** (ver ADR-002).

## Consequências

### Positivas
- **Isolamento:** o Zabbix só vê o Mosquitto local, não o broker público.
- **Reprodutibilidade:** `docker compose up -d` sobe o broker junto com a stack.
- **Latência controlada:** o Mosquitto local está na mesma rede Docker do Zabbix.
- **Migração futura:** quando o hardware real entrar, basta apontar o firmware
  para o Mosquitto local e desligar a bridge.

### Negativas
- **Um serviço a mais** no `docker-compose.yml` (mais um ponto de falha).
- **Configuração extra** (o `mosquitto.conf` precisa de `include_dir`).
- **Chown read-only** nos logs do container (cosmético, mas confunde).

### Neutras
- O broker local usa **anônimo** por enquanto (aceitável em laboratório).
- O `log_type notice` enche os logs, mas é útil para debug.

## Alternativas descartadas

### A) Usar só o broker público
- **O que era:** o Zabbix leria direto do `broker.emqx.io`.
- **Por que foi descartada:** expõe dados do CPD a terceiros; latência
  variável; o broker público pode cair a qualquer momento.

### B) Usar só o broker local (sem bridge)
- **O que era:** o firmware publicaria direto no Mosquitto local.
- **Por que foi descartada:** o Wokwi não alcança `localhost`. O hardware
  real até poderia, mas nesta fase o Wokwi é obrigatório.

### C) Fazer polling HTTP do ESP32 direto
- **O que era:** o Zabbix faria `http://IP-do-ESP32/status` a cada 30s.
- **Por que foi descartada:** o Wokwi não expõe HTTP; o firmware MQTT já
  está maduro; o polling HTTP exigiria reescrever o firmware.

## Referências

- `docker-compose.yml` (serviço `mosquitto`)
- `mosquitto/config/mosquitto.conf`
- `docs/03.txt` (batalha dos 4 erros do Mosquitto 2.x)

# ADR-002: Usar bridge MQTT em vez de conexão direta

- **Status:** Aceito
- **Data:** 2026-11-12
- **Autores:** Cristiano
- **Contexto do projeto:** Fatia 1 (Ponte MQTT)

## Contexto

O firmware do ESP32 (no Wokwi) publica no broker público (`broker.emqx.io`),
mas o Zabbix precisa ler os dados de dentro da rede Docker (`cpd-net`).

O Wokwi **não alcança `localhost`** (a rede `Wokwi-GUEST` só fala com a
internet pública). Portanto, não é possível apontar o firmware para o
Mosquitto local diretamente.

As opções eram:

1. **Bridge MQTT:** o Mosquitto local assina os tópicos do broker público
   e republica localmente com prefixo `publico/`.
2. **Expor o Mosquitto local à internet:** arriscado e frágil.
3. **Proxy HTTP:** o Mosquitto faria polling HTTP do broker público.

## Decisão

Usar uma **bridge MQTT** no Mosquitto local, configurada em
`mosquitto/config/conf.d/bridge.conf`.

A bridge assina os tópicos `rack_monitor_ABCD1234/*` no broker público e
republica no broker local com prefixo `publico/`:

```conf
topic rack_monitor_ABCD1234/status in 1 publico/ ""
topic rack_monitor_ABCD1234/ambiente in 1 publico/ ""
# ...
O publico/ é essencial para distinguir dados que vieram de fora dos
dados gerados localmente.

Consequências
Positivas
Isolamento: o Zabbix só vê dados com prefixo publico/, deixando
claro o que veio de fora.

Migração transparente: quando o hardware real entrar, basta apontar
o firmware para o Mosquitto local e desligar a bridge.

Cache local: se o broker público cair, o Mosquitto local continua
com as últimas mensagens (dependendo da configuração de retenção).

Negativas
Dependência do broker público: se o emqx.io cair, a bridge não
funciona.

Latência adicional: a mensagem passa pelo broker público antes de
chegar ao local (medido: < 1s).

Configuração extra: o bridge.conf tem sintaxe específica do
Mosquitto 2.x, que mudou em relação à 1.x.

Neutras
O firmware continua publicando no broker público (não muda nada).

A bridge usa cleansession true (se cair, reconecta do zero).

Alternativas descartadas
A) Expor o Mosquitto local à internet
O que era: abrir a porta 1883 do Mosquitto local para o Wokwi
alcançar.

Por que foi descartada: inseguro (exporia o broker à internet sem
autenticação); instável (dependeria do IP público do PC).

B) Proxy HTTP no Mosquitto
O que era: o Mosquitto faria polling HTTP do broker público a cada N
segundos.

Por que foi descartada: adiciona complexidade; perde a natureza
"push" do MQTT; o bridge é nativo do Mosquitto.

C) Firmware publicar direto no local
O que era: apontar o firmware do Wokwi para localhost:1883.

Por que foi descartada: impossível — o Wokwi não alcança localhost.

Referências
mosquitto/config/conf.d/bridge.conf

docs/03.txt (batalha dos 4 erros do Mosquitto 2.x)

Documentação oficial do Mosquitto sobre bridges

# ADR-003: Configurar o Zabbix via API (IaC) em vez de cliques

- **Status:** Aceito
- **Data:** 2026-11-12
- **Autores:** Cristiano

## Contexto

O Zabbix precisa de:

- 1 host (`esp32-cpd`)
- 1 item mestre (`mqtt_status.sh`, tipo External check)
- 9 itens dependentes (temperatura, umidade, porta, modo, etc.)
- 6 macros (`{$TEMP.ALERTA}`, etc.)
- 5 triggers (temperatura, porta, água, energia)
- 1 ação (envio de alerta via Telegram, quando implementado)

Configurar tudo isso **manualmente** na interface do Zabbix leva 15+ minutos

As opções eram:

1. **Interface do Zabbix** (cliques).
2. **API do Zabbix** via script Python (`configurar_zabbix.py`).
3. **Template YAML** importado manualmente.

## Decisão

Usar a **API do Zabbix** via script Python **idempotente**
(`configurar_zabbix.py`).

O script:

- Faz login na API.
- Verifica se cada recurso existe (get).
- Cria se não existe (create) ou atualiza se existe (update).
- Exporta o template YAML no final (para backup/importação).

**Padrão upsert** (update + insert): a mesma função lida com os dois casos,
evitando duplicação.

## Consequências

### Positivas
- **Reprodutibilidade:** `python configurar_zabbix.py` cria tudo em 2 segundos.
- **Idempotência:** rodar N vezes não duplica nada.
- **Versionamento:** o script está no Git, então a configuração é
  versionada junto com o código.
- **Documentação viva:** o script é a "fonte da verdade" da configuração.

### Negativas
- **Curva de aprendizado:** a API do Zabbix 7.0 tem regras específicas
  (`trends` só pode ser > 0 em float; `hostid` é imutável no update; etc.).
- **Debug mais difícil:** erros da API são menos amigáveis que a interface.
- **Testes necessários:** sem testes, uma mudança pode quebrar a
  idempotência silenciosamente.

### Neutras
- O template YAML é exportado no final (`zabbix/template_esp32_cpd.yaml`),
  servindo como "foto" do estado.
- Os IDs dos recursos são capturados dinamicamente (não hardcoded).

## Alternativas descartadas

### A) Configurar tudo na interface
- **O que era:** clicar item por item na UI do Zabbix.
- **Por que foi descartada:** não é reproduzível; 15+ minutos de cliques;
  erros de JSONPath são fáceis de cometer.

### B) Importar template YAML manualmente
- **O que era:** criar o template na UI, exportar YAML, importar em outro
  Zabbix.
- **Por que foi descartada:** a criação inicial ainda seria manual; a
  importação de template YAML não cobre macros/triggers/ações.

### C) Usar Zabbix Sender
- **O que era:** o ESP32 enviaria dados direto ao Zabbix via protocolo
  sender.
- **Por que foi descartada:** exigiria reescrever o firmware; perde a
  natureza MQTT; o push MQTT já é rápido o suficiente (< 1s).

## Referências

- `configurar_zabbix.py`
- `docs/05.txt` (automação via Python)
- `docs/08.txt` e `09.txt` (regras específicas da API do Zabbix 7.0)
- Documentação oficial da API do Zabbix 7.0

# ADR-004: Carregar o NOC 3D via iframe em vez de plugin nativo

- **Status:** Aceito
- **Data:** 2026-11-12
- **Autores:** Cristiano
- **Contexto do projeto:** Fatia 6 (NOC 3D)

## Contexto

O NOC 3D é uma sala isométrica renderizada com Three.js. Precisa ser exibida
dentro do Grafana, mas o Grafana tem restrições:

- O painel **Text** nativo **escapa HTML** por padrão (mesmo com a opção
  "HTML" selecionada).
- O painel **Business Text** aceita HTML, mas tem peculiaridades com
  `<script type="module">`.
- O Grafana tem **CSP** (Content Security Policy) que bloqueia scripts

As opções eram:

1. **Painel Text nativo** com HTML embutido.
2. **Business Text** com HTML/JS embutido.
3. **Iframe** apontando para um `noc3d.html` separado.

Usar um **iframe** apontando para `noc3d.html`, servido pelo próprio Grafana
em `/public/grafana-custom/noc/noc3d.html`.

O `noc3d.html` é uma página HTML **independente** que carrega o
`cena3d.js` via `<script type="module">` e recebe dados mockados (por
enquanto) ou reais (futuro).

Para o iframe funcionar, o `grafana.ini` precisa de 3 configurações:

```ini
[security]
disable_sanitize_html = true
allow_embedding = true
cookie_samesite = disabled

[panels]
disable_sanitize_html = true
Sem as 4 linhas, o navegador bloqueia o iframe silenciosamente (sem
erro visível no Console).

Consequências
Positivas
Isolamento: o Three.js roda no seu próprio "sandbox", sem as
restrições de CSP do Grafana.

Testável fora do Grafana: a URL noc3d.html funciona sozinha no
navegador, facilitando o debug.

Versionável: o noc3d.html e o cena3d.js são arquivos no Git.

Substituível: se o Grafana cair, o noc3d.html continua funcionando
(é uma página independente).

Negativas
Configuração extra: precisa de 4 linhas no grafana.ini.

Tamanho fixo: o iframe precisa de altura explícita (ex: 600px),
porque o painel não define altura para o container.

CORS (futuro): quando o noc3d.html for buscar dados reais do
Zabbix, precisará de proxy reverso ou CORS liberado.

Perde integração nativa: o painel Text/Business Text tem recursos
(variáveis, links, etc.) que o iframe não tem.

Neutras
O iframe é "invisível" para o usuário — ele vê o 3D, não o iframe.

O cena3d.js pode ser reutilizado em outros contextos (fora do Grafana).

Alternativas descartadas
A) Painel Text nativo com HTML
O que era: colocar o <script> do Three.js direto no painel Text.

Por que foi descartada: o Grafana 13 escapa HTML por padrão; o
[panels] disable_sanitize_html só funciona com a seção [panels] no
grafana.ini, que não é óbvia.

B) Business Text com HTML/JS
O que era: usar o plugin Business Text, que aceita HTML.

Por que foi descartada: o Business Text também bloqueou o
<script type="module"> (provavelmente por CSP interno); o iframe é
mais robusto.

C) Plugin customizado do Grafana
O que era: criar um plugin do Grafana para o NOC 3D.

Por que foi descartada: complexidade desnecessária; exigiria
compilar o plugin; o iframe resolve com 1/10 do esforço.

Referências
grafana/noc/noc3d.html

grafana/noc/cena3d.js

grafana/config/grafana.ini

docs/12.txt (batalha do CSP e iframe)

- **Data:** 2026-11-12

- Inseguro e instável.

- Impossível — o Wokwi não alcança localhost.

Regra de ouro: scripts Python complexos (com aspas triplas, JSON, etc.) sempre em arquivo .py, nunca via << 'PY'.

# 📡 Protocolo MQTT do Firmware RackMonitor v8.3

Este documento é o **contrato explícito** entre o firmware (ESP32) e o
consumidor (Zabbix, Grafana, NOC 3D). Qualquer mudança no firmware que
quebre este contrato deve ser **versionada** e documentada aqui.

**Versão do protocolo:** 1.0
**Versão do firmware:** 8.3
**Data:** 2026-11-12

---

## 🏗️ Arquitetura do fluxo
[ ESP32 ] ──publish──> [ broker público ] ──bridge──> [ Mosquitto local ] ──> [ Zabbix ] ──> [ Grafana ]
│ │
└──subscribe (comandos autenticados)──┘ │
│
[ NOC 3D (via API) ]

text

O ESP32 **publica** dados de sensores e **assina** comandos autenticados.
O Zabbix **lê** os dados via bridge MQTT. O Grafana **visualiza** via API do Zabbix.

# 🔐 Comandos Autenticados do Firmware RackMonitor v8.3

Este documento descreve o formato dos comandos autenticados que o
firmware aceita no tópico `rack_monitor_ABCD1234/comando`.

**Versão do protocolo:** 1.0
**Versão do firmware:** 8.3

---

## Formato geral
COMANDO|TS|NONCE|SIG

text

| Campo | Tipo | Descrição |
|---|---|---|
| `COMANDO` | string | Nome do comando (case-sensitive, MAIÚSCULO) |
| `TS` | number | Timestamp Unix (segundos). Informativo, não validado. |
| `NONCE` | number | Contador monotônico (uint64). Deve ser **maior** que o último. |
| `SIG` | string | HMAC-SHA256(`COMANDO|TS|NONCE`, chave_hmac).hex().toUpperCase() |

**Exemplo:**
DESARMAR|1762964400|15|A1B2C3D4E5F6...

text

---

## Comandos disponíveis

### 1. `ARMAR`

**Formato:** `ARMAR|TS|NONCE|SIG`

**O que faz:** arma o vigilante (se a porta estiver fechada).

**Resposta (se OK):**
```json
{"seq": 1, "cmd": "ARMAR", "ok": 1, "detalhe": "Armado.", "nonce": 15}
Resposta (se a porta estiver aberta):

json
{"seq": 2, "cmd": "ARMAR", "ok": 0, "detalhe": "Bloqueado: porta aberta. Feche a porta.", "nonce": 15}
2. DESARMAR
Formato: DESARMAR|TS|NONCE|SIG

O que faz: desarma o vigilante (se a porta estiver fechada).

Bloqueio: se a porta estiver aberta, o comando é recusado. Use
DESARMAR_EMERGENCIA se precisar desarmar com a porta aberta.

3. DESARMAR_EMERGENCIA
Formato: DESARMAR_EMERGENCIA|TS|NONCE|SIG|rack2026emg

O que faz: desarma o vigilante mesmo com a porta aberta.
Exige token adicional (rack2026emg).

Uso: situações de emergência (manutenção, falha de sensor, etc.).

4. STATUS
Formato: STATUS|TS|NONCE|SIG

O que faz: força a publicação do status no tópico status.

Rate limit: 10 segundos entre comandos STATUS.

5. TESTE
Formato: TESTE|TS|NONCE|SIG

O que faz: executa o autodiagnóstico (buzzer, LED, sensores).

Resposta (se OK):

json
{"seq": 5, "cmd": "TESTE", "ok": 1, "detalhe": "Modo teste agendado.", "nonce": 15}
6. PANICO
Formato: PANICO|TS|NONCE|SIG

O que faz: dispara o alarme de pânico (simula invasão).

Bloqueio: se o sistema estiver DESARMADO, o comando é ignorado.

7. RESET
Formato: RESET|TS|NONCE|SIG|rack2026

O que faz: zera todos os contadores (acessos, invasões, etc.).
Exige token adicional (rack2026).

Como o consumidor (Python, Grafana) deve assinar
Exemplo em Python:

python
import hmac
import hashlib
import time

CHAVE_HMAC = "sua_chave_hmac_aqui"  # mesma chave do firmware (NVS)
NONCE_ATUAL = 15  # deve ser maior que o último

def assinar_comando(comando, nonce):
    ts = int(time.time())
    payload = f"{comando}|{ts}|{nonce}"
    sig = hmac.new(
        CHAVE_HMAC.encode(),
        payload.encode(),
        hashlib.sha256
    ).hexdigest().upper()
    return f"{comando}|{ts}|{nonce}|{sig}"

# Exemplo
comando = assinar_comando("DESARMAR", 16)
# "DESARMAR|1762964400|16|A1B2C3D4E5F6..."
Atenção: o NONCE deve ser persistido entre chamadas (não pode
repetir). Se o consumidor reiniciar, deve ler o último nonce de algum
lugar (banco, arquivo, etc.).

Garantias de segurança
Garantia	Como é implementada
Autenticação	HMAC-SHA256 (chave em NVS)
Anti-replay	Nonce monotônico persistido em NVS
Integridade	HMAC cobre COMANDO|TS|NONCE
Token extra	RESET e DESARMAR_EMERGENCIA exigem token adicional
Case-sensitive	O comando é comparado em maiúsculas, mas o HMAC usa o original
Comandos de ambiente (sem HMAC)
O tópico rack_monitor_ABCD1234/comando/ambiente aceita comandos de
configuração de limiares sem HMAC:

Comando	Faixa	Padrão
SET_TEMP_ALERTA <v>	15–50 °C	30 °C

SET_UMID_ALERTA <v>	30–90 %	65 %
SET_UMID_CRIT <v>	40–100 %	80 %
PANICO	—	—
STATUS_AMB	—	—
Por que sem HMAC? Esses comandos não mudam o estado de segurança
(armado/desarmado), só ajustam limiares. O risco é baixo.

"""
test_schema.py — Testes do JSON Schema do status do firmware.
"""

import jsonschema
import pytest


def test_schema_valido(schema_status):
    """O schema é um JSON Schema válido."""
    jsonschema.Draft7Validator.check_schema(schema_status)


def test_payload_valido(schema_status, payload_status_valido):
    """Um payload real do firmware passa no schema."""
    jsonschema.validate(payload_status_valido, schema_status)


def test_payload_sem_campo_obrigatorio(schema_status, payload_status_valido):
    """Payload sem um campo obrigatório é rejeitado."""
    del payload_status_valido["temp_c"]
    with pytest.raises(jsonschema.ValidationError):
        jsonschema.validate(payload_status_valido, schema_status)


def test_payload_tipo_errado(schema_status, payload_status_valido):
    """Payload com tipo errado é rejeitado."""
    payload_status_valido["temp_c"] = "24.0"  # string em vez de number
    with pytest.raises(jsonschema.ValidationError):
        jsonschema.validate(payload_status_valido, schema_status)


def test_payload_estado_invalido(schema_status, payload_status_valido):
    """Payload com estado fora do enum é rejeitado."""
    payload_status_valido["estado"] = "ESTADO_QUE_NAO_EXISTE"
    with pytest.raises(jsonschema.ValidationError):
        jsonschema.validate(payload_status_valido, schema_status)


def test_payload_campo_extra(schema_status, payload_status_valido):
    """Payload com campo extra é rejeitado (additionalProperties: false)."""
    payload_status_valido["campo_novo"] = 42
    with pytest.raises(jsonschema.ValidationError):
        jsonschema.validate(payload_status_valido, schema_status)


def test_payload_temp_fora_da_faixa(schema_status, payload_status_valido):
    """Temperatura fora da faixa (-50 a 100) é rejeitada."""
    payload_status_valido["temp_c"] = 150
    with pytest.raises(jsonschema.ValidationError):
        jsonschema.validate(payload_status_valido, schema_status)


def test_payload_umid_fora_da_faixa(schema_status, payload_status_valido):
    """Umidade fora da faixa (0 a 100) é rejeitada."""
    payload_status_valido["umid_pct"] = 150
    with pytest.raises(jsonschema.ValidationError):

🎯 Por que testes agora? (E por que não os outros itens)
Boa pergunta. Vou ser honesto: testes agora é a escolha certa, mas não por ser "mais importante" que os outros. É por ordem de dependência e custo de mudança.

🧠 O raciocínio por trás da ordem
Testes (#5) antes do NOC real (#7)
O NOC 3D real (#7) vai consumir os dados do Zabbix. Para isso, ele precisa saber:

Quais campos existem no status (o schema).

Quais valores são válidos (os enums).

Quais garantias o firmware oferece.

Se você fizer o NOC real sem testes, e depois o firmware mudar (ex: renomear temp_c para temperatura), o NOC vai quebrar silenciosamente. Os testes pegam isso antes de chegar no NOC.

Analogia: é como construir a fundação antes da casa. O NOC real é o telhado; os testes são a fundação.

Testes (#5) antes da observabilidade (#9)
A observabilidade (Prometheus) é sobre medir o pipeline. Mas para medir, você precisa saber o que é "normal". Os testes definem o "normal" (o contrato do firmware). Sem eles, a observabilidade mede... o quê?

Analogia: é como calibrar um termômetro antes de usá-lo. Os testes são a calibração.

Testes (#5) antes da escalabilidade (#10)
A escalabilidade (adicionar uma segunda sala/CPD) depende de confiar no que já existe. Se você adiciona uma segunda sala e o configurar_zabbix.py tem um bug, você vai debugar duas vezes (na sala 1 e na sala 2).

Os testes garantem que o script funciona antes de você replicá-lo.

Analogia: é como testar o molde antes de fazer 10 cópias.

⚖️ Por que não fazer o LICENSE agora?
O LICENSE (#2) é importante, mas é independente de tudo. Ele não bloqueia nem é bloqueado por nenhum outro item. Pode ser feito a qualquer momento, inclusive no final.

Além disso, o LICENSE é uma decisão jurídica, não técnica. Você pode querer pensar melhor sobre qual licença usar (MIT, Apache 2.0, GPL) antes de commitar. Deixar para o final dá tempo para decidir com calma.

🏗️ A ordem completa, justificada
Ordem	Item	Por que nessa posição
1º	Testes (#5)	Fundação: define o que é "correto"
2º	NOC real (#7)	Consome o contrato, precisa dos testes
3º	Escalabilidade (#10)	Replica o que já está testado
4º	Observabilidade (#9)	Mede o que já está estável
5º	LICENSE (#2)	Independente, pode ser o último
🎯 O que os testes vão desbloquear para o NOC real
Quando você for fazer o NOC real (#7), o noc3d.html vai precisar:

Buscar dados do Zabbix (via API).

Validar os dados contra o status-schema.json.

Atualizar a cena 3D com os dados validados.

O passo 2 (validar) só faz sentido se o schema estiver testado. Se o schema estiver errado (ex: temp_c como string em vez de number), o NOC real vai quebrar.

Os testes garantem que o schema está correto. Sem eles, o NOC real é uma aposta.

🚨 O risco de fazer o NOC real sem testes
Imagine este cenário:

Você faz o NOC real agora (sem testes).

O noc3d.html busca os dados do Zabbix e renderiza.

Funciona... mas o schema tem um bug: temp_c está como number, mas o firmware envia como string em algum caso.

O NOC real renderiza "NaN°C" em vez de "24.5°C".

Você passa horas debugando o NOC real, achando que o problema é no iframe, no CORS, no Grafana...

Quando o problema era no schema.

Os testes pegam o bug no passo 3, antes de chegar no NOC.
