Script de criação (cole inteiro no Terminal)
Salve como criar-monitoramento-cpd.sh em qualquer lugar (ex.: ~/Downloads) e rode com bash criar-monitoramento-cpd.sh. Ou cole direto no Terminal — funciona igual.

bash
#!/usr/bin/env bash
# =============================================================
# monitoramento-cpd — cria estrutura e arquivos do Passo 0
# Testado em macOS (Apple Silicon, arm64)
# =============================================================
set -euo pipefail

BASE="$HOME/monitoramento-cpd"

if [ -d "$BASE" ]; then
  echo "⚠️  A pasta $BASE já existe."
  read -r -p "Sobrescrever os arquivos (mantendo o .env se existir)? [s/N] " resp
  case "$resp" in
    [sS]*) echo "→ Seguindo, sobrescrevendo arquivos (exceto .env)..." ;;
    *) echo "Abortado."; exit 0 ;;
  esac
else
  echo "→ Criando $BASE"
fi

# ---------- Pastas ----------
mkdir -p "$BASE"/{mosquitto/config/conf.d,zabbix,grafana,docs}

# ---------- .gitkeep ----------
touch "$BASE/mosquitto/config/conf.d/.gitkeep" \
      "$BASE/zabbix/.gitkeep" \
      "$BASE/grafana/.gitkeep"

# ---------- .gitignore ----------
cat > "$BASE/.gitignore" <<'EOF'
# Segredos e configuração local
.env
*.local

# Dados dos containers
data/
logs/

# IDE / SO
.vscode/
.idea/
*.swp
.DS_Store
Thumbs.db

# Python
__pycache__/
*.pyc

# Mosquitto (se um dia mudar o volume para pasta local)
mosquitto/data/
mosquitto/log/
EOF

# ---------- .dockerignore ----------
cat > "$BASE/.dockerignore" <<'EOF'
.git
.gitignore
.env
*.md
docs/
.vscode/
EOF

O erro é do zsh, não do script 🎯
O zsh (shell padrão do macOS) tem uma opção chamada histverify (ou BANG_HIST) ligada por padrão em algumas configurações. Ela interpreta ! como expansão de histórico e, quando vê !) no meio do texto, tenta expandir e falha com event not found: ).

Onde está o problema: dentro do echo final do script tem:

bash
echo "→ .env criado a partir do .env.example (edite as senhas!)"
O ! antes do ) no zsh interativo dispara a expansão de histórico. Em bash funciona, em zsh não.

Além disso, quando você colou o script inteiro no Terminal (em vez de rodar como arquivo .sh), o zsh processou interativamente e explodiu nesse ponto — por isso você vê zsh: event not found: ).

Duas soluções (use a que preferir)
Solução A (recomendada) — rodar como arquivo .sh, não colar no Terminal
Quando o script roda como arquivo (bash arquivo.sh), o ! não sofre expansão de histórico (isso é um recurso interativo). Então basta:

Salvar o script num arquivo (ex.: ~/Downloads/criar-monitoramento-cpd.sh)

Rodar com bash, não com zsh:

bash
bash ~/Downloads/criar-monitoramento-cpd.sh
Não precisa nem chmod +x se usar bash arquivo.sh diretamente.

Como salvar no Mac sem quebrar nada: abra o TextEdit, cole o conteúdo, Format → Make Plain Text, salve como criar-monitoramento-cpd.sh em ~/Downloads. Depois bash ~/Downloads/criar-monitoramento-cpd.sh.

Ou no Terminal com nano:

bash
nano ~/criar-monitoramento-cpd.sh
# cola, Ctrl+O, Enter, Ctrl+X
bash ~/criar-monitoramento-cpd.sh
Isso resolve porque o ! só é problema em sessão interativa do zsh, não em scripts executados.

Solução B — trocar o ! por algo seguro no script
Se você preferir colar no Terminal mesmo, ou quiser blindar o script para qualquer shell, troque:

bash
echo "→ .env criado a partir do .env.example (edite as senhas!)"
por:

bash
echo "→ .env criado a partir do .env.example (edite as senhas)"
Ou seja, remova apenas o !. Nada mais no script depende dele. Faça a troca no arquivo antes de rodar.

Dica para o futuro (evitar o problema de novo)
Se você costuma colar comandos com ! no Terminal do Mac, tem duas saídas permanentes:

Opção 1 — desligar a expansão de histórico no zsh (perde o recurso !!, !$ etc.):

bash
echo 'unsetopt BANG_HIST' >> ~/.zshrc
source ~/.zshrc
Opção 2 — usar aspas simples ao redor de strings com ! no Terminal interativo:

bash
echo 'texto com ! e ) dentro'
Aspas simples no zsh desativam a expansão de !. É o que o script já faz nos cat <<'EOF' — o único ponto que escapou foi o echo final com aspas duplas.

Por que ~/ e não o Desktop?
Foi uma escolha consciente do script:

~/ é o padrão da maioria dos projetos (fica em home do usuário).

No Docker Desktop do Mac, o file sharing padrão cobre ~/ — então o bind mount ./mosquitto/config funciona sem configuração extra.

O Desktop também funciona (o Docker Desktop inclui ~/Desktop no compartilhamento), mas ~/ é mais neutro.

Se você preferir no Desktop ou em outro lugar (ex.: ~/Desktop/Casa/monitoramento-cpd), é fácil mover depois de estabilizar:

bash
# NÃO mova agora (containers estão referenciando o path).
# Espere o Passo 0 fechar e mova com a stack parada:

cd ~/monitoramento-cpd
docker compose down
mv ~/monitoramento-cpd ~/Desktop/Casa/use/monitoramento-cpd
cd ~/Desktop/Casa/use/monitoramento-cpd
docker compose up -d
Os volumes nomeados (postgres_data, grafana_data, etc.) não estão presos ao path — eles vivem no Docker, não na pasta. Então mover a pasta não perde dados. Só o bind mount ./mosquitto/config é relativo, e continua funcionando após mover.

Resumo: está em /Users/cristiano/monitoramento-cpd. Abre com open ~/monitoramento-cpd e segue para o docker compose up -d. 🚀

⚠️ Um detalhe importante do Docker Desktop no Mac
O file sharing padrão do Docker Desktop inclui ~/ — o que cobre ~/Desktop/monitoramento-cpd (Desktop é subpasta de ~). Então deve funcionar direto.

Mas, em alguns Macs, o Docker Desktop tem permissões restritas para Desktop, Documents e Downloads (macOS exige consentimento por pasta). Se o docker compose up -d falhar com algo como:

text
error while creating mount source path '.../mosquitto/config': mkdir ...: permission denied
ou o cpd-mosquitto ficar reiniciando com erro de leitura de mosquitto.conf, a causa é essa. Solução:

Abra Docker Desktop → Settings (ícone de engrenagem) → Resources → File sharing

Confirme que /Users/cristiano está na lista (o padrão inclui)

Se /Users/cristiano/Desktop estiver fora, adicione-o e clique em Apply & restart

Ou, se preferir evitar o problema: System Settings → Privacy & Security → Files and Folders → Docker e permita acesso a "Desktop Folder".

No macOS Sonoma/Sequoia, o mais comum é o Docker já ter permissão por ~/. Mas vale saber onde olhar se algo falhar.
